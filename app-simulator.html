DONE Lens detection now works on phones that are not in the model database, which is most of them. Three fixes, all measured on a Redmi Note 11S: physical sub-cameras are enumerated (not just cameraIdList); unlisted ids are probed read-only, which is how MIUI hides the ultra-wide — it reports six cameras to dumpsys and exactly two to getCameraIdList(); and lenses are classified by 35mm-equivalent focal length relative to the device's own main sensor instead of raw focal length. The old rule (focal < 3mm = ultra-wide) called three of that phone's four back cameras ultra-wide, including a 2MP macro and a 2MP depth sensor — those are now dropped as auxiliaries, since on this phone not one camera declares DEPTH_OUTPUT. Result: zoom chips went from a fake 1x/2x/5x digital crop to the real 0.6x + 1x. Brand is read from Build.BRAND so a Redmi says Redmi, not Xiaomi, with a coloured monogram beside it — a letter, not the maker's logo, because logos are trademarks and a letter also works for a brand nobody has entered
DONE Camera2 diagnostics screen (Settings > Device > Camera2 capabilities): every capability the device reports, as structured JSON, with the numbers that matter while picking a lens always visible and the rest behind an animated per-section "See more". Found 8 cameras on the S23 Ultra where cameraIdList alone shows 4 — the ultra-wide and tele have no top-level id, only physical sub-ids. Two rules it holds to: nothing may throw (a diagnostic that crashes on the odd HAL is useless on exactly the device worth diagnosing), and absent is not the same as unsupported (a field the HAL does not publish stays in the report as an explicit null and shows as "—", so "not supported" and "never asked" stay distinguishable). Exports via the system share sheet or the clipboard; the on-screen technical half is rendered from the exported JSON itself, so screen and file cannot drift apart. Verified by an on-device instrumentation test that runs the real probe against the real HAL
DONE Manual exposure rebuilt as a camera control, not two sliders: ISO and shutter now snap to a 1/6-stop series — the standard third-stop values (100, 125, 160, 200…) with the geometric midpoint between each pair rounded to a camera-looking number (110, 140, 180…), so 37 ISO positions and 53 shutter positions across this sensor instead of 19 and 33, every familiar value still exactly where it was, and no two detents ever showing the same label. Slider lengthened to 260dp and each stop crossed gives a CLOCK_TICK haptic, because at this density the eye cannot confirm a one-stop nudge mid-drag. Values are real again (ISO 400, 1/60 — not ISO 174, "1/47"), and the rail collapsed to value-carrying chips that slide one slider out on tap. The fast end and ISO are whatever the sensor really reports — the old code clamped to 1/8000 and ISO 100, an S23 Ultra does 1/18571 and ISO 50. The slow end stops at 1/24 by policy, not by hardware: exposure time bounds frame rate, so 1/24 is exactly 24fps and anything slower is a slideshow (this sensor's true 0.15s limit is 6fps). A long shutter also sets SENSOR_FRAME_DURATION, without which Camera2 silently clamped it back to the frame interval, and the panel shows the fps that costs in amber (measured: 1/10s really captured at 11fps, which is what the floor now prevents)
DONE Found the real cause of the "fake pixelation filter" in vertical: it was not the scaling filter, it was the viewfinder being bound at 320x240 and blown up across a 1440x2560 view (confirmed in dumpsys media.camera). CameraX's ResolutionSelector matches its bound size against sensor-orientation sizes and never rotates it, so a 9:16 request for 608x1080 meant "nothing wider than 608" and everything above it was discarded. Bound is now sensor-oriented and capped by pixel budget instead of a 1920x1080 box: 9:16 went 320x240 -> 1920x1080 (27x), 3:4 640x480 -> 1440x1080, 16:9 1440x1080 -> 1920x1080. The streamed video was never affected, which is why OBS looked fine and the phone did not
DONE PC Control from app (start/stop) — now also called automatically before streaming, not just from Settings buttons
DONE Zero-touch connect: USB now auto-forwards on plug-in (PC-side watcher, no adb/python command), Wi-Fi auto-discovers + auto-starts PC services — Install_FrameCast.vbs is the only manual step, once, and it's completely silent (no console ever)
DONE Fixed receiver crash-loop: services were launched as bare scripts instead of `-m pc_receiver.x`, so receiver.py died on import on every single start — invisible since output went to devnull. Now module-launched, single bind + per-connection error isolation, logs to file
DONE Fixed cmd window flashing on repeat: CREATE_NO_WINDOW alone didn't stop adb.exe from popping a console under the hidden pythonw.exe parent — needed DETACHED_PROCESS + stdin redirection too. Also removed a stale pre-VBS Startup shortcut that pointed at a visible-console .bat
DONE PC service now gated on OBS: FrameCast_Service.vbs is a lightweight WMI watcher (no ports, no processes) that only starts control_server.py while obs64.exe/obs32.exe is actually running, and stops the whole tree when OBS closes — was previously "always on from login"
DONE Real H.264 encoding replaces per-frame JPEG: H264Encoder.kt (MediaCodec, buffer-mode) on the phone, PyAV-backed h264_decoder.py on the PC. Video bitrate setting now actually configures the encoder. Not yet verified on real camera hardware — no device in this sandbox — but PC-side decode has real encode/decode round-trip tests
DONE Fixed the real reason OBS got nothing on record: adb reverse failing once (a race right after USB authorization, confirmed in the wild) marked that device as "handled" forever, so the tunnel just never came up for the rest of the session. Now retries every poll cycle until it actually succeeds. Also hardened CameraStreamer against a H264Encoder construction failure silently killing frame delivery
DONE Fixed viewfinder looking like a cheap pixelation filter at low resolutions (e.g. 360p): PreviewView defaulted to "performance" mode (SurfaceView/hardware-overlay scaling, blocky at large upscale factors on some GPUs) — switched to "compatible" mode (TextureView, proper GPU bilinear filtering), so a real low-res capture now looks like real low-res video, not a mosaic effect. The preview genuinely captures at the chosen resolution either way, that part was never fake
DONE Fixed "PC not reachable" over USB: adb reverse silently fails outright ("more than one device/emulator") the moment a phone shows up twice in `adb devices` — which happens for a single phone with USB connected AND wireless debugging paired at the same time. Now every reverse call targets a specific device via -s instead of hoping only one is attached
DONE Found the real reason no video ever reached the PC: the YUV->Bitmap conversion feeding both encoders bulk-copied camera planes assuming zero row padding, which real camera HALs routinely violate (this code path was never exercised on real hardware before now). A stride mismatch there silently broke every single frame, uncaught, on the analyzer thread — no crash, camera just never showed up. Rewritten stride-aware, matching the approach already used on the encode side
DONE Fixed "Cannot reach PC" over WiFi: Settings' PC-control actions (Start PC, Check, speed test...) fell back to 127.0.0.1 — the phone's own loopback — whenever no IP had been manually discovered first. Now auto-discovers the same way the main streaming flow already did. (PC-side firewall/discovery both checked and confirmed working; if this still fails, the router may have client/AP isolation enabled between WiFi devices — outside what either side of this app can fix)
DONE Real audio capture + transmission. Every audio setting now drives something real instead of being a saved preference with nothing behind it: an AudioRecord + MediaCodec AAC-LC encoder, the platform NoiseSuppressor, and a 100Hz low-cut for the wind filter (whose frequency response is unit tested — 20Hz cut to under 10%, speech flat within 5%). Audio and video share one socket as tagged chunks with timestamps from a single clock, so the PC can line them up; it decodes AAC and plays into a virtual audio cable (VB-CABLE/VoiceMeeter), which your conferencing app then picks as its microphone. A phone with no microphone permission, or whose AAC encoder won't start, streams video exactly as before — audio failing never costs you the camera. Verified end to end on the PC alone via `demo_sender --audio`; the on-device capture path still needs a real phone
